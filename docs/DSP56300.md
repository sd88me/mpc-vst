# Porting a DSP56300/gearmulator engine to MPC OS

Findings from the Xenia port (`ports/xenia/`, started 2026-09-25), generalised for any future port whose
engine comes from [gearmulator](https://github.com/dsp56300/gearmulator) — the project that emulates classic
DSP56300-based hardware synths by running their original firmware on emulated silicon. Read this before
starting a second one; it should save re-deriving the build and CPU findings from scratch.

**Status: the central question (does the DSP56300 interpreter run fast enough on MPC's ARM CPU) is not yet
confirmed against real firmware.** See "CPU: the open question" below. This doc will be updated once Xenia's
device test (`ports/xenia/devtest.sh`) reports real numbers; treat the interpreter-throughput figures here as
a lower bound on what any DSP56300 port needs to clear, not a verdict.

## What gearmulator covers

One codebase, several device libraries sharing the same DSP56300/MC68k emulation core:

| Emulator | Hardware | Device lib | Notes |
|---|---|---|---|
| Osirus | Access Virus A/B/C | `axel/virusLib/` | |
| OsTIrus | Virus TI/TI2/Snow | `axel/virusLib/` | shares virusLib with Osirus |
| Vavra | Waldorf microQ | `waldi/microq/mqLib/` | gearmulator's own docs note audio dropouts at low latency, root-caused to an HDI08 rate-limit setting (`doc/vavra_xenia_comparison.md` in gearmulator, not vendored here) -- a data point if a Vavra port ever chases similar glitches |
| **Xenia** | Waldorf Microwave II/XT | `waldi/xt/xtLib/` | **ported here, see `ports/xenia/`** |
| Nodal Red 2x | Nord Lead/Rack 2x | `claudia/n2x/n2xLib/` | |
| JE-8086 | Roland JP-8000 | `ronaldo/je8086/jeLib/` | |

They all sit on the same shared libraries (`source/framework/{synthLib,baseLib,hardwareLib}`) and the same
`source/cpu/dsp56300` (DSP) + `source/cpu/mc68k` (Musashi-based MC68k) or, for some, an H8S core instead of
MC68k. A future port of any of these starts from the same recipe as Xenia, below.

## Vendoring recipe

Vendor into the port's own repo (`src/gearmulator/`, upstream's folder layout preserved), never fetched at
build time -- see `ports/xenia/src/VENDORED.md` for the exact pattern and commit-hash bookkeeping to copy.
What to bring in, generalised from Xenia's table:

| Path | What | Every port needs it? |
|---|---|---|
| `source/framework/{synthLib,baseLib,hardwareLib}` | device base class, resampler, MIDI, LCD/flash chip models | yes |
| `source/cpu/dsp56300/source/{dsp56kEmu,dsp56kBase}` | DSP56300 emulator | yes |
| `source/cpu/dsp56300/source/asmjit/src` | asmjit (the JIT's assembler) | yes -- compiled even when the JIT never runs, see below |
| `source/cpu/mc68k` | MC68k emulator (Musashi) | if the device uses one (Xenia, microQ, Nord Lead 2x do) |
| `source/3rdparty/libresample` | resampler synthLib uses | yes |
| the device's own lib (`xtLib`, `virusLib`, `mqLib`, `n2xLib`, `jeLib`) | ROM loader, board/DSP glue, state, sysex | yes, that one |
| the maker's `common/` lib if the device has one (`waldi/common/wLib` for microQ+XT) | shared board glue | if it exists for that maker |

Leave out: the JUCE plugin/UI code (`framework/juce/`), the other synths, `tools/`, tests, upstream's own
CMake files (a hand-written `Makefile` replaces them -- see below), IDE project files, and anything
platform-specific this port doesn't need (Windows/macOS-only sources).

Licence: gearmulator and dsp56300 are GPL-3.0. Check the specific device lib's dependencies too (Musashi and
asmjit each carry their own permissive licences).

## The three patches every 32-bit ARM DSP56300 build needs

dsp56300's JIT only has x86-64 and AArch64 (64-bit ARM) backends. MPC OS runs a 32-bit ARM process, so the
DSP always runs on the interpreter (`DSP56K_FORCE_INTERPRETER=1`) here -- but the JIT *source* is still always
compiled (`DSP` owns a `Jit` unconditionally), and it picks its codegen target with `HAVE_X86_64`/`HAVE_ARM64`,
neither of which a 32-bit ARM compiler defines. Three small, verified patches make it compile (Xenia's copies,
identical fixes needed for any other device lib built the same way):

1. **`source/cpu/dsp56300/source/dsp56kBase/buildconfig.h`**, appended: with `DSP56K_FORCE_INTERPRETER` set and
   neither `HAVE_X86_64` nor `HAVE_ARM64` defined, define `HAVE_X86_64`. Points the never-run JIT source at the
   x86 emitter so it compiles; `HAVE_X86_64` is read nowhere else outside the JIT except `dspconfig.h`'s JIT
   switch, which the interpreter flag already overrides.
2. **`source/cpu/dsp56300/source/dsp56kEmu/jitops_helper.cpp`**: `static_assert(sizeof(m_interruptFunc) == 8)`
   → `static_assert(!g_jitSupported || sizeof(m_interruptFunc) == 8)`. A function pointer is 4 bytes on 32-bit
   ARM; the check only matters when the JIT actually runs.
3. **`source/framework/synthLib/buildconfig.h`** (added, not a patch): upstream generates this from
   `buildconfig.h.in` via CMake (`SYNTHLIB_DEMO_MODE` off); without CMake, write the generated form directly.
   Upstream's own `.gitignore` hides it from a plain `git add`, so commit it with `git add -f`.

Also needed: `-DASMJIT_STATIC -DASMJIT_NO_AARCH64` on the whole core (asmjit's own multi-arch support isn't
needed when only the x86 emitter is ever built for a 32-bit target).

Exact diffs: `ports/xenia/src/VENDORED.md`'s "Local changes" section. Full context and how they were found:
`docs/NOTES.md`'s Xenia entry.

## Build pattern: a separate core library

`vst2_wrap.c` (this repo's wrapper) is plain C (`gcc -std=gnu11`; it does `void*`-to-typed-pointer conversions
a C++ compiler rejects). A DSP56300 engine is C++17. So the emulator core is built as its own static library
(`ports/xenia/core/Makefile`) with a hand-rolled Makefile, not CMake (upstream's CMakeLists.txt files are kept
for reference only, not driven directly -- reproducing their exact source lists by hand, minus tests/debugger/
profiler glue and the unused JIT arch's `_aarch64.cpp`/`_x64.cpp` files, is more portable than teaching this
repo's Docker-based build to run CMake). The port's own `mpc_engine()` translation unit links against that
static library. Same `arm32v7/gcc:12` image `tools/build_port.sh` already uses, so the ABI matches.

Two build variants of the core, same Makefile: `SANITIZE=1` (ASan/UBSan, host, for `tools/test_port.sh`) and
the plain optimised one (armhf, for the device). See `ports/xenia/build.sh` / `test.sh` for the exact
invocations, and `ports/xenia/tools/interp_bench.cpp` / `xenia_probe.cpp` for how to link a standalone tool
against just the core library (no `mpc_engine()` wrapper needed) for benchmarking.

## CPU: the open question

Every DSP56300-based synth's firmware programs the chip's clock through its PLL (`ESSI`/`ESXI` in the
emulator), and gearmulator's DSP is cycle-driven: real-time audio needs the interpreter to execute that many
emulated DSP cycles per second on one host core. `getDspClockHz()` on the device object reports the
programmed clock once booted; gearmulator also logs it ("Clock speed changed to: N Mhz"). The real DSP56300
silicon tops out around 100-150 MHz depending on the part; different firmwares run their PLL at different
fractions of that, so **the actual number to beat is per-synth, found by booting that synth's real ROM**, not
a fixed constant.

Measured so far (`ports/xenia/tools/interp_bench.cpp`, a synth-like loop -- parallel moves, MACs, modulo
addressing -- not any specific firmware, so this number is a reasonable proxy across the whole DSP56300
family, not Xenia-specific):

| Machine | Interpreter throughput |
|---|---|
| x86-64 Xeon @ 2.8 GHz (cloud build host, one core) | ~61 MIPS = ~71 MHz of DSP clock |
| MPC/Force, Cortex-A17 @ 1.8 GHz (`performance` governor) | **13.6 MIPS = 15.9 MHz of DSP clock** (measured 2026-09-25) |

The device sustains about **22% of the x86 host's interpreter throughput**. That is a real, device-measured
number (not a guess), and it's the ceiling: no DSP56300 firmware requiring much more than ~16 MHz of DSP
clock will run in real time on this class of ARM core without help. **What is still unconfirmed is whether
Xenia's actual firmware clock falls under that ceiling** -- `xenia_probe` (same tool family, boots the real
ROM and holds chords at several DSP-clock percentages) is built and was pushed to a device, but the ROM
upload failed on every attempt so far (see `docs/NOTES.md`'s Xenia entries and the session history around
2026-09-25 for the debugging trail -- BusyBox `od` flag incompatibility, then a truncated multi-ssh-call ROM
transfer, both now fixed in `ports/xenia/devtest.sh`). **Update this section once that boots and reports
real speed/voice numbers.**

If a future DSP56300 port's firmware needs meaningfully more than ~16 MHz (Virus and Virus TI plausibly do --
they're later, more complex designs than the Microwave II/XT), the interpreter alone is very unlikely to be
enough; run that port's own `interp_bench`-style check and a `xenia_probe`-style firmware boot test *before*
committing to a full skin/parameter port, not after.

## If the interpreter isn't enough: options, roughly by effort

1. **A DSP clock parameter** (Xenia's `dsp_clock`, 50-100%): trades polyphony/fidelity for headroom. Free,
   always worth having regardless of whether it's needed.
2. **A voice cap**: if a firmware's own voice allocator doesn't shed load gracefully under a slow clock (drops
   audio quality across all voices instead of stealing voices cleanly), capping note-on count in the engine
   adapter is a small, targeted fix. Needs the real firmware test to know if and where it's needed.
3. **A 64-bit helper process**, only on units whose kernel is actually 64-bit (check per Akai model --
   `tools/probe_device.sh`'s "arch" line; the Force tested here is armv7l, 32-bit): run the DSP in a separate
   process compiled for AArch64, using gearmulator's fast JIT, with audio handed back over shared memory.
   Real engineering work (a new process boundary, IPC, lifecycle management) but reuses gearmulator's existing
   JIT rather than writing a new one.
4. **gearmulator's own DSP bridge** (`framework/networkLib/` + `framework/tools/bridge/`, not vendored for
   Xenia since it wasn't needed): the DSP runs on a separate networked computer, audio/MIDI over the network.
   Existing, tested upstream code; moves the CPU problem off the MPC entirely at the cost of needing a second
   machine and adding network latency.
5. **A 32-bit ARM (AArch32/Thumb-2) JIT backend for dsp56300**: the only fix that raises the interpreter's own
   ceiling rather than working around it -- gearmulator's existing AArch64 JIT gets roughly 40x over the
   interpreter (5.8 -> 234-421 MIPS in gearmulator's own perf history), so even a conservative fraction of that
   would change the calculus for every DSP56300 port, not just one. A large, multi-thousand-line compiler-
   backend project (new `JitReg`/`JitRegGP` mapping, 56-bit accumulator handling without native 64-bit
   registers, AAPCS32 calling convention, per-op backends for `jitops_agu/alu/ccr/helper/jmp`, verified
   instruction-for-instruction against the interpreter via gearmulator's own `interpreterunittests.cpp`).
   Realistically weeks of focused compiler-backend work, and its failure mode (a silently wrong opcode
   translation) is much harder to catch than the other options' failure modes. Only worth it if (1) the 64-bit
   helper process is unavailable (the target unit's kernel really is 32-bit-only) and (2) more than one
   DSP56300 port is planned, so the investment amortises.

## Device suitability testing before committing to a port

`ports/xenia/tools/interp_bench.cpp` (no ROM needed) and `xenia_probe.cpp` (boots the real firmware, holds
chords at several DSP-clock settings, reports speed/level/thread-CPU) are written to be a reusable template,
not Xenia-specific in structure. `ports/xenia/devtest.sh` packages both into a tarball that runs from `/tmp`
on the device, next to a running MPC, with no install and no restart -- copy this pattern for the *first*
thing to run on a candidate DSP56300 synth, before writing any skin or parameter mapping: it answers the CPU
question in an afternoon instead of after a full port's worth of work.
